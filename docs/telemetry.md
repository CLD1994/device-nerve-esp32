# 统一 STATE 状态流验证

## 线格式与范围

目标 500 Hz（2 ms）固定宽度十六进制 STATE，12 个 token，含 LF 82 字节。每帧含启动身份、设备时间低32位、两路独立序号/年龄/有效位和四个有符号测量值，详见[协议](protocol.md#数据面统一状态流目标-500-hz周期-2-ms)。无效路使用明确占位，工具解码成缺失值，不作为零测量。原四字段 STATE、VEL_VALID 及 CART_STATE1 不再输出或兼容。

模型与双路运动工具要求两路有效，vel 小车调试仅要求小车路；真实 FAULT 不被豁免。默认编码器采样 2 kHz，速度窗名义约 16 ms，与报告或推理频率是不同概念。

调度目标来自 `components/telemetry/telemetry_timing.h`。超过周期后重新基准，不追赶补发历史帧；但高优先级任务、UART 锁和发送缓冲仍可导致延迟。默认 FreeRTOS tick 为 1 kHz，编译检查可表示 1 ms 的节拍。不能以此声称实机严格周期。

## 带宽及未验证边界

8N1 每字节10位。460800 baud 单方向理想容量 46080 B/s；STATE 占 41000 B/s（约89.0%），余 5080 B/s 给 MODE/EVENT/回复等，不是确定的延迟预算。当前 Kconfig 默认1000000，但现场可为460800，必须按真实构建匹配，不能假定1M。下行命令为另一方向，不与上行直接相加，CPU、UART锁及USB调度仍共享资源。

512字节发送缓冲在460800下约11.1 ms；缓冲不能增加带宽。大诊断响应要求停止状态，但短查询/事件仍可能引入突发。低波特率不足以覆盖82字节500Hz，不能只扩缓冲掩盖。500Hz实际帧率、尾延迟及400Hz模型闭环时序须现场验证，本次软件测试不证明通过。

设备 tick 的相对推进可识别会话基线后的积压增长；采样年龄与主机接收后年龄不能证明初始恒定传输延迟不存在。不可直接相减主机与设备绝对时间。重复序号不刷新状态，重启/倒退/长断流须停止并重建会话。没有CRC，UNKNOWN=0不能证明不存在仍合法的数值损坏或整帧遗漏。

## 不驱动电机的验收

保持 DISABLED，关闭其它串口占用，以现场 COM11/460800 为例：

```powershell
python tools/cartpole_host.py --port COM11 --baud 460800 query
python tools/cartpole_host.py --port COM11 --baud 460800 state --secs 30 --expected-hz 500
```

状态命令不发送运动目标。频率±1Hz、无未知行只是接收验收，不是有效性、物理比例或端到端延迟证明。检查多次长采集、帧间隔/尾延迟、排队和有效路变化；不要逐帧打印而拖慢接收。未解决通信异常前不据平均频率扩大运动范围。

## 无硬件回归

```bash
bash host_tests/test_telemetry_timing.sh
python -m unittest discover -s tools -p 'test_*.py'
```

Python需要pyserial，测试用替身不连接串口。格式回归覆盖四种有效组合、极值、环绕、无效占位、过期、重复及损坏；目标ESP-IDF构建与跨仓库消费者验证另记录，均不替代硬件验收。
